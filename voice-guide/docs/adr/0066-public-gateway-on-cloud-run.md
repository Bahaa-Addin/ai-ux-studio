# ADR-0066: The public gateway runs on Google Cloud Run, not Fly.io, and the visitor's address is the last entry of X-Forwarded-For

- Status: Proposed (2026-11-15; accepted when the first deploy passes the runbook's checks, the forged-address check included)
- Date: 2026-11-15
- Area: deployment, privacy, cost; amends ADR-0053 §2 (the client address) and §3 (packaging); follows ADR-0055 (Whisper on Modal) and ADR-0047 (VoiceTut)
- Owner decision: 2026-11-15, after comparing costs, "Ok Let's use Modal and Cloud Run instead"

## Context

ADR-0053 packaged the public gateway for Fly.io. Fly has no free allowance for accounts created after 2024-10-07 (https://fly.io/docs/about/discontinued-plans/), so the demo would pay from its first hour.

Google Cloud Run has a monthly free tier per billing account. In a Tier 1 region such as europe-west1 it is, for request-based billing, 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests, and for instance-based billing 240,000 vCPU-seconds and 450,000 GiB-seconds (https://cloud.google.com/run/pricing). It needs a billing account (Firebase's Blaze plan or a Google Cloud billing account) even when the bill is $0.

VoiceTut (ADR-0047) and Whisper (ADR-0055) stay on Modal, unchanged. Only the gateway moves.

## Decision

1. **One Cloud Run service**, `vg-public-demo`, in `europe-west1`, running the image built from `deploy/gateway/gateway.Dockerfile`. Settings, each with its reason:
   - `--port=8080`: Cloud Run injects `PORT` (8080 by default) and the gateway listens on it.
   - `--cpu=1 --memory=1Gi`: the memory Fly's machine had (1 GB); one vCPU where Fly had two shared ones. Not tuned: no load has been measured. Cloud Run's filesystem is in memory (see Consequences), so the 1 GiB also holds the speech cache's files.
   - `--max-instances=1`: sessions live in memory, so a second instance would not know a visitor's session. Cloud Run says the maximum "can be exceeded for a brief period due to circumstances such as traffic spikes" (https://docs.cloud.google.com/run/docs/configuring/max-instances); at demo scale that is rare, and the cost is that a visitor starts again.
   - `--min-instances=0`: nothing runs, and nothing is billed, when nobody visits.
   - `--no-cpu-throttling` (instance-based billing): with request-based billing, the default, CPU is allocated only while a request is processed; with instance-based billing it is allocated for the instance's life (https://docs.cloud.google.com/run/docs/container-contract). The gateway sends VoiceTut work after it has replied (fire-and-forget) and has timers, so it needs CPU between requests.
   - `--concurrency=400`: Fly's hard limit, kept.
   - `--timeout=3600`: the request timeout is 300 s by default and 3600 s at most. A server-sent-events stream is cut at the timeout and the browser's `EventSource` reconnects; the longest timeout means one cut an hour.
   - `--allow-unauthenticated`: visitors are the public. The gateway checks the site key itself (`x-vg-site-key` or `?k=`) and, when an `Origin` is sent, that it is one of the site's origins (`siteFor` in `services/gateway/server.ts`).
   - `--service-account=vg-gateway@<project>.iam.gserviceaccount.com`: see 3.
   - Non-secret settings, as `fly.toml` set them: `VG_PUBLIC=on`, `VG_STORE=memory`, `VG_TRAIL=on`, `VG_LLM_PROVIDER=anthropic`, `VG_LLM_EFFORT=low`, `VG_AGENT_TOKENS_PER_SITE_DAY=3000000`, `VG_VOICETUT_SENTENCES_PER_DAY=300`, `VG_STT_SECONDS_PER_DAY=14400`, `VG_RATE_TURNS_PER_MIN=20`; and now `VG_CLIENT_IP_HEADER=x-forwarded-for`.
   - `VG_PUBLIC_URL` is known before the first deploy: the deterministic address is `https://SERVICE-PROJECT_NUMBER.REGION.run.app`, only when the label `SERVICE-PROJECT_NUMBER` is at most 63 characters (https://docs.cloud.google.com/run/docs/triggering/https-request). The tool computes it from the project number and refuses a longer label.
2. **The visitor's address is the last entry of `X-Forwarded-For`.** This amends ADR-0053 §2, which keyed the rate limits on `fly-client-ip`. Cloud Run's front end (the `run.app` address) appends the caller's address as the last entry; any entries before it are whatever the caller sent. `clientIp(req, 'x-forwarded-for')` therefore returns the last non-empty entry, trimmed, and falls back to the socket address when the header is missing or empty. Any other trusted header (Fly's `fly-client-ip`, for instance) behaves as before, and with no trusted header the first entry is still used, for local runs.
   - **Evidence, and its limit.** The evidence is one test on a `run.app` service reported on Google's developer forum (https://discuss.google.dev/t/cloud-run-which-client-ip-can-i-safely-use-for-rate-limiting/409611): with no header sent the service saw `OBSERVED`; with `192.0.2.1` sent it saw `192.0.2.1, OBSERVED`. **Google does not document this behaviour.** It is not verified on our service.
   - **The forged-address check** is therefore part of the deploy. After a deploy (and on demand with `--check <url>`), the tool sends the turn limiter's burst plus 5 (15 with the default `VG_RATE_BURST` of 10) `POST /v1/turn` requests for the site at the same time, each with a different forged `X-Forwarded-For`. `/v1/turn` takes the turn limiter right after the body is read and before the session is looked up (`services/gateway/server.ts`, the `/v1/turn` route). Each answer is classified. The gateway's own 429 (code `rate_limited`) means the limiter ran on a key the turns shared, since each forged value is used once: one such answer passes the check. A 404 `no_session` is a turn the limiter let through (the body names no session). Only when every turn is let through is the deployment called forgeable: then the last-entry rule does not hold, the rate limits do not protect it, the check fails and the extension is not shared. Anything else (a 401 or 403 for the site key or origin, a 5xx, a 429 from Cloud Run's front end) means the check could not run; it fails, says so, and is run again. Sending the requests together means a slow link cannot let the limiter refill between them.
   - **With a load balancer in front** the last entry would be the balancer's, not the visitor's. This design is for the `run.app` address only.
3. **Secrets in Secret Manager, under a dedicated service account.** The gateway runs as `vg-gateway`, never as the default compute account. `vg-gateway` holds only `roles/secretmanager.secretAccessor`, granted on each secret it reads, not on the project. Secrets reach the container as environment variables (`--set-secrets`, version `latest`):
   - required: `VG_SECRET` from `vg-secret`, `VG_ADMIN_TOKEN` from `vg-admin-token`, `ANTHROPIC_API_KEY` from `anthropic-api-key`;
   - optional, both or neither: `VG_WHISPER_URL` from `vg-whisper-url` with `VG_WHISPER_TOKEN` from `vg-whisper-token`;
   - optional: `VG_VOICETUT_URL` from `vg-voicetut-url`.
   The tool lists the project's secrets and stops, naming it, when a required one is missing or when only one half of the Whisper pair exists. The gateway's own start-up checks (ADR-0053 §2) still refuse an unsafe setting.
4. **Builds come from the committed tree only.** `tools/deploy-cloudrun.ts` resolves `--ref` (default `HEAD`) to a commit, archives `voice-guide` and `experiences` from that commit with `git archive` into a fresh temporary directory, puts the commit's `gateway.Dockerfile` at its root as `Dockerfile` and its ignore file `gateway.Dockerfile.dockerignore` as `.dockerignore`, and builds with Cloud Build (`gcloud builds submit`) into Artifact Registry as `<region>-docker.pkg.dev/<project>/vg/gateway:<short sha>`. Uncommitted changes in those two folders are never deployed; the tool warns when there are some and says so. Nothing is built from the working tree, so what runs is a commit that can be named. The `gcloud` command is run with argument arrays, never a shell string. Secrets reach the service only as Secret Manager references: the tool refuses a secret's variable among the plain settings, in any case. Each step awaits its command, so a signal is seen while the command runs. Ctrl-C in the terminal reaches the running `gcloud` too, which cancels and exits; a SIGTERM sent to the tool alone is passed on to the running command; either way no later step starts and the local temporary copy is removed. What already reached Google stays: the uploaded source in Cloud Build's staging bucket (`gs://<project>_cloudbuild/source`) and any image already pushed. `--dry-run` prints every command and runs nothing.
5. **Region `europe-west1`**, a Tier 1 region for the free tier above, as a knob (`--region`). Other regions were not checked against the free tier.
6. **`deploy/gateway/fly.toml` is removed.** `deploy/gateway/gateway.Dockerfile` is unchanged apart from the command in its header comment. ADR-0053's other decisions (the loader, the public mode's start-up refusals, tap to hear, the VoiceTut cap, the accessibility button) stand.

## Consequences

- The filesystem is in memory: "writing to it uses the instance's memory" and it is lost when the instance stops (https://docs.cloud.google.com/run/docs/container-contract). The speech cache writes only known lines (plan words, fixed phrases; ADR-0047 §2) to `<dataDir>/speech`, and the Docker image has no `data/`, so the cache starts empty on every cold start. The first lines of a day are new VoiceTut sentences, which count against `VG_VOICETUT_SENTENCES_PER_DAY` (300); past it visitors hear the browser voice.
- Sessions are in memory. A restart or a scale-down to zero forgets them (people start again, as ADR-0053 already said). A brief second instance would split sessions: a visitor whose request lands on the second one has no session there.
- Streams end at 60 minutes and reconnect.
- A billing account is needed even when the bill is $0. The runbook adds a budget alert in Cloud Billing; Google's budgets send alerts and do not cap spending (https://cloud.google.com/billing/docs/how-to/budgets).
- Cold starts: the first request after scale-down waits for the container to start. How long has not been measured.
- SIGTERM comes 10 seconds before SIGKILL when an instance stops (container contract). The memory store is lost at a stop either way (above); whether anything else in the gateway's shutdown needs longer has not been checked.
- The memory store, `maxInstances=1` and instance-based billing are each a cost or a risk the owner can change with one flag.

## Pilot knobs

The tool's options: `--project` (required), `--region` (`europe-west1`), `--service` (`vg-public-demo`), `--repo` (`vg`, the Artifact Registry repository), `--service-account` (`vg-gateway@<project>.iam.gserviceaccount.com`), `--ref` (`HEAD`), `--dry-run`, `--check <url>`.

The service's flags: `--max-instances` (1), `--min-instances` (0), `--no-cpu-throttling` (on), `--concurrency` (400), `--timeout` (3600), `--cpu` (1), `--memory` (1Gi). The settings of ADR-0053 and ADR-0055 (`VG_RATE_TURNS_PER_MIN`, `VG_AGENT_TOKENS_PER_SITE_DAY`, `VG_VOICETUT_SENTENCES_PER_DAY`, `VG_STT_SECONDS_PER_DAY`) are unchanged.

## Revisit when

- A load balancer or a custom domain goes in front of the service: the last entry is then not the visitor, and the client-address rule must change.
- Sessions must survive restarts or more than one instance is needed: Postgres on Cloud SQL, or Firestore.
- The free tier is exceeded (Cloud Run's metrics and the budget alert show it).
- Google documents `X-Forwarded-For` differently, or the forged-address check fails after a platform change.

## Verified by

- `tests/unit/public-config.test.ts`: `clientIp` with `x-forwarded-for` returns the last non-empty entry, trimmed; two different forged prefixes in front of the same last entry give the same key; a single entry gives itself; a missing or blank header gives the socket address; the existing tests still pass. The new test was written first and seen to fail on the old `clientIp`.
- `tests/unit/deploy-cloudrun.test.ts`: `deployArgs` carries each setting of decision 1; the tool's `ENV`, the `VG_PUBLIC_URL` from `publicUrl` and dummy required secrets pass the gateway's own `checkPublicConfig(loadPlatformConfig(env), env)` with no problems; dropping any required secret is caught by `secretFlags`; `publicUrl` has the documented format and refuses a label over 63 characters; Whisper is both-or-neither and VoiceTut optional; a secret's variable among the plain settings is refused (in any case), and `--set-secrets` holds only `name:latest` references; with an injected runner and `fetch`, gcloud is never called; the forged-address check passes on a fake that gives the gateway's 429 after 10 calls, fails on one that never does, passes on the real `RateLimiter` when each answer takes 1.1 s, and classifies each answer (gateway 429 beside a front-end 429: pass; all front-end 429s, all 503s or 401s: could not run, never "forgeable"; all let through: forgeable); a real SIGTERM sent to the tool by the build's child process ends the build at once with no deploy, and a real SIGINT stops the run before the deploy; the temporary directory is removed and the listeners are gone afterwards.
- Tests that failed first. The reviews of 2026-11-15 (two reviewers, then a skeptic over the fixes) found: an assertion that could not fail, a check that a slow link or a front-end 429 could fool, a broken gateway reported as forgeable, and signals never seen while `spawnSync` blocked (a SIGTERM let the deploy run). The non-gateway 429, slow-link and plain-secret tests failed on the tool before the fixes (4 of its 13 tests failed then, the fourth an earlier signal test since replaced by the two below); the two signal tests fail when their fix is removed (SIGTERM not passed on: the build runs its 30 s and the test fails; no check after a step: the deploy runs; no listeners: the test process is killed).
- A local run of the image (2026-11-15, Docker Desktop 27.4.0 on the owner's Mac, built from this change; the tool's `ENV` and `VG_PUBLIC_URL`, dummy secrets, 1 CPU and 1 GB): the gateway started in public mode in about 3 s, with no refusal, the committed knowledge base seeded and `/health` ok. `--check` passed through a stand-in for the front end that appends the caller's address (answers: ten 404, then five 429) and failed straight at the container, where nothing appends it (fifteen 404: forgeable). This shows the tool, the image and the gateway's limiter together; it does not show what Cloud Run's real front end does.
- **Not verified: no deploy has run.** No `gcloud` command of this change has been run against a project. That the front end appends the visitor's address as the last entry rests on the forum test above, not on Google's documentation and not on our service. That `--no-cpu-throttling` and the free-tier numbers keep the bill at $0 for this demo's traffic has not been measured, nor has the cold-start time. The runbook's checks, the forged-address check first among them, are what accept this ADR.
