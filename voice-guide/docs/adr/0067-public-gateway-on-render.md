# ADR-0067: The public gateway runs on Render's free plan, with Render's free Postgres, and the visitor's address is Cloudflare's CF-Connecting-IP

- Status: Proposed (2026-11-15; accepted when the first deploy on Render passes the runbook's checks)
- Date: 2026-11-15
- Area: deployment, privacy, cost; supersedes [ADR-0066](0066-public-gateway-on-cloud-run.md); amends ADR-0053 §2 (the client address) and §3 (packaging); follows ADR-0055 (Whisper on Modal) and ADR-0047 (VoiceTut)
- Owner decision: 2026-11-15, "Actually, I changed my mind on Cloud Run because I found that Render is free and doesn't need any linked cards and has a free Postgres database we can use." Asked for the database, with the 30-day expiry stated, the owner chose "Render's free Postgres" (not the memory store). Asked how the code reaches Render, the owner said "I'll push it myself".

## Context

ADR-0066 chose Google Cloud Run over Fly.io. Cloud Run needs a billing account even when the bill is $0, and the owner prefers to link no card. Nothing was deployed on Cloud Run.

Render's free plan needs no card (https://render.com/docs/free). What it gives, from Render's documentation (https://render.com/docs/free, https://render.com/docs/compute-plans, https://render.com/docs/web-services):

1. **A free web service**: 0.1 CPU and 512 MB. 750 free instance hours per workspace per month; when they are used up, all free services are suspended until the month's end. It spins down after 15 minutes with no inbound traffic, and spinning up takes "about one minute". It may be restarted at any time. One instance only. No persistent disk: local files are lost on redeploy. Outbound ports 25, 465 and 587 are blocked.
2. **A free Render Postgres**: 0.1 CPU, 256 MB, 1 GB of storage, at most 100 connections, **no backups**. **It expires 30 days after creation; after a 14-day grace period Render deletes it and all its data.** One free database per workspace.
3. **Bandwidth and builds**: since 1 August 2026 a free (Hobby) workspace includes 5 GB of outbound bandwidth a month (then $0.15/GB) and 500 build minutes. This is from a third-party summary of Render's "New Workspace Plans" document, not from Render's page itself. Without a payment method Render suspends free services when bandwidth runs out instead of charging.

VoiceTut (ADR-0047) and Whisper (ADR-0055) stay on Modal, unchanged. Only the gateway moves.

## Decision

1. **A Blueprint, `render.yaml`, at the repository root** (its default place; https://render.com/docs/blueprint-spec). The owner pushes `feature/live-way2` to GitHub and connects Render to the repository; nothing in our work pushes or calls Render. One web service, `vg-public-demo`, and one database, `vg-public-db`. Settings, each with its reason:
   - `type: web`, `runtime: docker`, `dockerfilePath: ./voice-guide/deploy/gateway/gateway.Dockerfile`, `dockerContext: .`: the image is built from the repository root, as ADR-0053 §3 requires (the SDK build bundles `../experiences`). Render builds with BuildKit and honours `.dockerignore`; BuildKit also reads `<Dockerfile>.dockerignore` next to the Dockerfile, which is why `deploy/gateway/gateway.Dockerfile.dockerignore` exists.
   - `plan: free`: no card.
   - `region: frankfurt`: the Render region nearest Egypt. The region is fixed once the service is created. The database uses the same region, so the gateway reaches it on Render's private network.
   - `branch: feature/live-way2`.
   - `healthCheckPath: /health`.
   - `autoDeployTrigger: off`: deploys are by hand. The branch gets many commits, builds are limited to 500 minutes a month, and an untested commit should not go live by itself.
   - `PORT=8080`: the gateway reads `VG_PORT` (8080 in the image), not `PORT`. `PORT` tells Render which port to send requests to; its default is 10000 and it can be overridden (https://render.com/docs/web-services), so it is set to match the image. The gateway binds every address, 0.0.0.0 included.
   - Plain settings, as ADR-0066 had them: `VG_PUBLIC=on`, `VG_TRAIL=on`, `VG_LLM_PROVIDER=anthropic`, `VG_LLM_EFFORT=low`, `VG_AGENT_TOKENS_PER_SITE_DAY=3000000`, `VG_VOICETUT_SENTENCES_PER_DAY=300`, `VG_STT_SECONDS_PER_DAY=14400`, `VG_RATE_TURNS_PER_MIN=20`. New: `VG_STORE=postgres`, `VG_KB_SEED=committed`, `VG_CLIENT_IP_HEADER=cf-connecting-ip` (2 below) and `VG_DB_POOL_MAX=5` (a 0.1-CPU database). Values are strings.
   - `VG_PUBLIC_URL` is not set. `services/shared/config.ts` takes `VG_PUBLIC_URL`, then `RENDER_EXTERNAL_URL`, then `http://localhost:<port>`. Render sets `RENDER_EXTERNAL_URL` on web services to the full `https://<name>.onrender.com` URL (https://render.com/docs/environment-variables). `VG_PUBLIC_URL` still wins when both are set.
2. **The visitor's address is `CF-Connecting-IP`.** This amends ADR-0053 §2 and replaces ADR-0066 §2 for hosting.
   - **Why not `X-Forwarded-For`.** Render's services sit behind Cloudflare. Render's proxy appends to `X-Forwarded-For` and never strips what the caller sent, so the header reads `<caller's own entries…>, <visitor>, <Cloudflare edge>`. Neither its first nor its last entry is the visitor. Cloudflare sets `CF-Connecting-IP` (and `True-Client-IP`) to the visitor's address (https://rohitpaulk.com/articles/render-rails-remote-ip, quoting Render support).
   - **Evidence, and its limit.** That is a third-party article quoting Render support. **Render does not document it.** It is not verified on our service.
   - **The check is part of the deploy.** `npm run gateway:check -- <url>` (`tools/check-public-gateway.ts`) first reads `GET /health`, itself sending forged client-address headers: it must be 200 with `ok: true` and `clientHeader: true`. Two fields are new on `/health`, and neither shows an address:
     - `clientHeader`: whether the trusted client-address header was present and non-empty on that request (`false` when none is configured). If the host drops the header, `clientIp` falls back to the socket address, which is Render's proxy: every visitor would share one rate-limit key and the forged-address check below would still pass. Because the check's own request forges the header, a host that passes the caller's header through, or a gateway reached without its front end, shows `true` here and is then caught as forgeable below.
     - `clientKey`: the first 8 hex characters of SHA-256 over a salt made once per process and the caller's rate-limit key. The same caller gets the same value, another network another one; it cannot be reversed to an address and means nothing outside that process. The check reads `/health` twice with two different forged values and fails when the key changes with them: the gateway would then key on a value the caller sends. It prints the key, and the runbook asks for a second run from another network: the same key from two networks means everyone is keyed on one address (a case a 429 alone cannot show).
     - `boot`: a random id of the process. A restart (Render's sleep, a deploy) makes a new salt, so two client keys compare only under the same boot id; the runbook says to make the second-network run within 15 minutes and to run both again when the boot id changed.
     - What the second-network run can miss: if everyone were keyed on Cloudflare's edge address (for example `VG_CLIENT_IP_HEADER=x-forwarded-for` on Render, whose last entry is the edge), it shows two keys only when the two networks reach Render through different edge addresses. That has not been checked; the deployed setting is `cf-connecting-ip`, which `render-blueprint.test.ts` holds.
   - Then it sends the turn limiter's burst plus 5 `POST /v1/turn` requests at the same time, each forging **all three** of `X-Forwarded-For`, `CF-Connecting-IP` and `True-Client-IP` with values unique to that turn, so the check holds whichever header the deployment trusts. Each answer is classified as in ADR-0066: the gateway's own 429 (`rate_limited`) is proof; a 404 `no_session` is a turn let through; all let through means forgeable; anything else (401 or 403 named, a 5xx, a front-end 429) means the check could not run. It exits 0 or 1.
   - **`clientIp` keeps its `x-forwarded-for` last-entry rule** (ADR-0066 §2). It is right for Cloud Run and harmless here, since Render's deployment trusts `cf-connecting-ip`. Fly's `fly-client-ip` also behaves as before.
   - **An IPv6 visitor counts by their /64 network** (`addressKey` in `services/shared/http.ts`, on every host). One visitor usually holds a whole /64 and could otherwise send each turn from another address in it and get a fresh limit each time (100 turns at once all passed before this rule, in the review's test). The address is checked with `net.isIPv6` and written out in full first (a dotted IPv4 tail included); an IPv4-mapped address (`::ffff:0:0/96`, in any form) and a NAT64 address (`64:ff9b::/96`) count as their IPv4 address; a Teredo address (`2001:0::/32`, whose low 64 bits are the client's) counts whole; IPv4, and anything that is not a valid address, as given. The gap was older than this ADR; the review of 2026-11-15 found it.
3. **Render's free Postgres, as the store.** The service gets `DATABASE_URL` from the database (`fromDatabase`, `connectionString`). The gateway creates its tables when it starts (`PostgresStore.connect` migrates; `services/shared/store/schema.sql` is idempotent), and `VG_KB_SEED=committed` activates the committed knowledge base in an empty database (`services/gateway/main.ts`). Sessions and traces therefore survive sleeps and restarts. `ipAllowList: []` allows only Render's private network (the gateway); nobody on the internet can connect. Database settings: `plan: free`, `region: frankfurt`, `postgresMajorVersion: "16"`, `databaseName: voiceguide`, `user: voiceguide`.
4. **Secrets are generated by Render or entered in its dashboard, never in the repository.** `VG_SECRET` and `VG_ADMIN_TOKEN` use `generateValue: true` (a random value, made once). `ANTHROPIC_API_KEY`, `VG_WHISPER_URL`, `VG_WHISPER_TOKEN` and `VG_VOICETUT_URL` use `sync: false`: Render asks for them once, at Blueprint creation. Left empty, the gateway treats them as unset. The gateway's own start-up checks (ADR-0053 §2) still refuse an unsafe setting.
5. **Deploys are manual** (Manual Deploy, then Deploy latest commit), of the branch the owner pushed.
6. **The Cloud Run tool is removed**: `tools/deploy-cloudrun.ts`, its test and the `deploy:cloudrun` script. Its post-deploy check lives on as `tools/check-public-gateway.ts` (`npm run gateway:check`), host-independent and free of child processes. `deploy/gateway/gateway.Dockerfile` changes only a header comment.

## Consequences

- **The database expires 30 days after creation and is deleted 14 days later.** The runbook has a monthly step: create a new database, redeploy the gateway. Tables, the committed knowledge base and the experience profile are recreated at start. Everything else in the old database is lost: sessions, traces, the day's quota counters (they start again from zero), cached items and hand-off tokens (page watch and the trail's aggregate are off in public, so their tables are empty). If the step is missed, the gateway cannot start once the database is gone.
- **Cold start.** The first visitor after 15 quiet minutes waits for Render's spin-up (about a minute, Render's figure), then the gateway's start and the first session. Measured with Docker on the owner's Mac at Render's free sizes (2026-11-15; the gateway `--cpus=0.1 --memory=512m`, Postgres 16 `--cpus=0.1 --memory=256m`; the committed image with the same settings for the first start and the first restart, the image of this change with `render.yaml`'s own settings for the second restart): the first start on an empty database took 41.8 s and, in a later run, 33.0 s (tables made, knowledge base seeded), starts on a database already filled 37.4 s and 28.6 s, and the first session after a start 5.5 s. So the total is up to about 1.5 to 2 minutes, and the extension's guide may give up first. That has not been measured.
- **Speed once awake.** In the same run, turns took 0.1 to 0.6 s by replay ("إيه أرخص باقة نت", "What's the cheapest internet bundle?") and 0.4 to 1.0 s when routed to the agent ("Where can I recharge my line?"; the agent itself was not called, the key was a dummy). With the memory store they took 0.1 to 0.4 s.
- **Memory.** The gateway used 94 to 108 MB of its 512 MB, the database 29 to 35 MB of its 256 MB; the database held 8.4 MB after seeding, of its 1 GB.
- **Data in the EU.** Traces and sessions (masked words only, ADR-0021, kept 7 days) now sit in Render's Postgres in Frankfurt instead of only in memory.
- **Bandwidth.** 5 GB a month. A 3 s VoiceTut sentence is about 144 KB, estimated at 24 kHz mono 16-bit, not measured. Without a card Render suspends the service when the bandwidth runs out.
- **Hours.** 750 a month cover one always-on service. When they are used up, free services are suspended to the month's end.
- **No backups.** What the gateway cannot recreate (the list in the first bullet) is lost if the database is.
- Render may restart the service at any time; Postgres keeps the sessions through that.
- Streams: Render's proxy request limit is 100 minutes, from Render's own articles; it is not on the web-services page.

## Pilot knobs

The Blueprint's fields: `plan`, `region`, `branch`, `autoDeployTrigger`, `healthCheckPath`, `ipAllowList`, `postgresMajorVersion`. The settings: `VG_STORE`, `VG_KB_SEED`, `VG_CLIENT_IP_HEADER`, `VG_DB_POOL_MAX` (5), `PORT` (8080), `VG_PUBLIC_URL` (unset: `RENDER_EXTERNAL_URL`). The settings of ADR-0053 and ADR-0055 (`VG_RATE_TURNS_PER_MIN`, `VG_AGENT_TOKENS_PER_SITE_DAY`, `VG_VOICETUT_SENTENCES_PER_DAY`, `VG_STT_SECONDS_PER_DAY`) are unchanged. The check: `npm run gateway:check -- <url> [--site <id>]` (`--site` defaults to `vodafone-eg`).

## Revisit when

- The 30-day renewal becomes a burden: a non-expiring Postgres, such as a paid Render plan or another provider.
- The cold start loses visitors: a paid instance, or a keep-awake ping (which would use about 744 of the 750 hours).
- Render documents client addresses differently, or the forged-address check fails after a platform change.
- Bandwidth or hours run out.

## Verified by

- `tests/unit/public-config.test.ts`: `RENDER_EXTERNAL_URL` gives `publicUrl` when `VG_PUBLIC_URL` is unset, and `VG_PUBLIC_URL` wins when both are set (written first and seen to fail); with `cf-connecting-ip` trusted, `clientIp` returns that header's value, ignores any `X-Forwarded-For`, and falls back to the socket address when the header is missing; IPv6 addresses count by their /64 (100 addresses of one /64 give one key; written first and seen to fail); `addressKey` on the mapped, hex-mapped, NAT64, dotted-tail, Teredo and invalid forms; `trustedHeaderPresent` and `clientKeyFingerprint` (salted: not the plain hash of the key), which `/health` uses.
- `tests/unit/public-health.test.ts`: the real `GET /health` of a gateway on the memory store and a free port: `clientHeader` true with the header and false without, the same `clientKey` for the same caller whatever `X-Forwarded-For` says, another for another caller, one for one IPv6 /64, an 8-hex `boot` that stays the same, and no address in the answer (seen to fail without the `boot` field).
- `tests/unit/render-blueprint.test.ts`: the root `render.yaml`, parsed with the `yaml` package, carries each setting of decisions 1, 3 and 4; its plain values with dummy values for the two generated secrets and `ANTHROPIC_API_KEY`, and a `RENDER_EXTERNAL_URL`, pass the gateway's own `checkPublicConfig(loadPlatformConfig(env), env)` with no problems; no setting holds a value for a secret name; `DATABASE_URL` points at the database's name; the service and the database share a region; `dockerfilePath` exists; `PORT` equals the Dockerfile's `VG_PORT`; `ipAllowList` is empty; `autoDeployTrigger` is `off`.
- `tests/unit/check-public-gateway.test.ts`: the ported classification, front-end 429, slow-link (real `RateLimiter`, mocked `Date`) and refused-key tests; `clientHeader: false` fails the check; each turn forges all three headers with unique values; a stand-in Cloudflare that overwrites `CF-Connecting-IP` with one visitor address (through the real `clientIp(req, 'cf-connecting-ip')` and `RateLimiter`) passes, and one that passes the caller's `CF-Connecting-IP` through, or adds nothing, fails as forgeable (seen to fail before `/health` sent a forged header); a client key that follows the forged header fails at `/health` before any turn is sent; a `/health` that answers 503 says to run again; the client key, boot id and second-network step are printed; an unknown `--site` says so without a stack trace.
- End to end with Docker (2026-11-15, the owner's Mac): the image of this change, `render.yaml`'s own plain settings plus what Render provides (`RENDER_EXTERNAL_URL`, `DATABASE_URL`, generated secrets, empty optional ones), on Postgres 16, both at Render's free sizes. The gateway started and seeded the empty database. `npm run gateway:check` passed through a stand-in Cloudflare that overwrites `CF-Connecting-IP` (ten 404, then five 429) and with one visitor rotating IPv6 addresses inside one /64 (keyed on the /64); through a stand-in that passes the caller's header through, and straight at the gateway with no front end, it failed at `/health` because the client key followed the forged value, before sending a turn. No error in the gateway's log. The times and memory are in Consequences.
- Reviews of 2026-11-15: two reviewers over the first version (9 findings: a check that a shared key could still pass, the IPv6 gap, an untested `/health` rule, an unknown `--site` stack trace, a quote style; and four doc corrections), then a skeptic over those fixes (6 findings: a second-network comparison that a restart could fool, hence `boot`; the real `/health` untested, hence `public-health.test.ts`; a fingerprint assertion that failed about once in 700 runs; IPv6 forms keyed wrongly, hence `net.isIPv6` and full expansion; an x-forwarded-for example stated as fact; three runbook wordings), all fixed.
- **Not verified: no deploy has run.** Nothing has been pushed or sent to Render. That Cloudflare's `CF-Connecting-IP` reaches the gateway on Render rests on a third-party article quoting Render support, not on Render's documentation; the stand-ins show only that the gateway and the check do the right thing if it does. The cold start on Render itself has not been measured. The 5 GB bandwidth figure comes from a third-party summary. The runbook's checks, the forged-address check and the second-network run first among them, are what accept this ADR.
