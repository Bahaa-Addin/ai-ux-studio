# The eshop in the knowledge base and in the Pocket: cross-check (2026-11-13)

I read the files on disk and contacted no live site. I changed nothing in the repository and ran no tests or browsers. My scratch scripts are in `/tmp/claude-501/xcheck` (`money.py`, `cache.py`, `norm.mts`). HEAD is now 94688ad (S5 committed). Another session is editing `record.js`, `live-adapter.js`, `store.js` and `demo-browser.ts`. The line numbers below are from the files as they are now.

**In five lines**
- The knowledge base has no eshop page. The guide already runs on eshop pages in the demo browser. The experience layer and the Pocket never do.
- The most urgent risk exists today. On eshop pages the fallback agent has nothing to avoid, because the knowledge base marks 0 commit points, and its click tool never checks the guard. Fix this before anything else.
- Only the Playwright crawler can take the eshop. It needs several safeguards before the owner runs it once.
- **Reading 1** fits phase 3 as it stands: web cards that link to the eshop show in the album (S7, S13). **Reading 2**, the Pocket running on eshop pages, needs saved eshop pages first, plus its own ADR and sub-phase.
- `npm run demo:live -- --replay` says it is offline, but it is not for eshop links. Every eshop link opens the live shop.

## 2. Where the maps disagree, and which is right

1. **demo-browser.ts line numbers.** The layer-pocket, rules-privacy and offline-inventory maps cite older lines. kb-crawler's are current. Today: layer origin :106, origin check :123, layer conditions :139-141, DOMContentLoaded :154, microphone :227, gateway routes :261-266.
2. **Money strings: 294 or 265.** Both are right about different things. I measured 294 matching strings. About 264-265 are visible text (labels, target texts, descriptions). The other 30 are ids, CSS selectors and collection ids built from price text. That last part matters: **prices are in ids**, so a price change renames destinations.
3. **Cached eshop JavaScript: 170, 183 or 187. Dated entries: 204 or all.** offline-inventory is right: 187 JavaScript files, and all 228 entries are dated 12 Nov. The 170 and 183 counts are subsets.
4. **Accessibility widget on the eshop: absent, or unknown?** layer-pocket is right that the audit records it as absent (audit:95, 2026-10-23). rules-privacy is right that no newer evidence is on disk. Treat it as "recorded absent", and re-check it once in the owner's live check.
5. **Which crawler `npm run sync` uses.** offline-inventory says the in-browser crawler would produce empty pages. That is wrong: the sync uses the Playwright crawler (`ingest-lib.ts:54`). kb-crawler and rules-privacy are right.
6. **Replay and eshop requests.** offline-inventory says unsaved shop requests get a 1x1 picture or are aborted. That rule applies only to hosts *outside* `site.origins` (`demo-browser.ts:373`). The eshop is inside, so its pages open live (`:387`).
7. **"A record has no origin field"** (layer-pocket). Not quite: `origin` exists but means who kept the sticker (`record.js:32, 50`). The new field must have another name, for example `source.origin`.
8. **Commit words.** kb-crawler says "add to cart" is missing from the word list. True, but "buy now" and "اشتري" are already in it. What actually blocks detection is the rule that only a submit button inside a form counts (`extract.ts:322-324`). rules-privacy is right on that.
9. **"robots.txt blocks /cart at any depth"** (rules-privacy). This rests on the reconstructed test text. The real eshop rules are unknown until the file is saved verbatim.
10. **ADR number.** The maps say "after 0053 and 0054", "ask the owner" and "in ADR-0053". The owner's rule from 2026-11-10 is that ADRs are numbered in the order they are written. The phase 3 map's 0053 (S11) and 0054 (S13) are only reservations, so the first eshop ADR written takes 0053 unless the owner says otherwise.
11. **Distinct eshop links: 26 or 28.** I measured 28 raw URLs, and 23 when only `categoryUrls` is kept. The counts differ only by how URLs were normalised. Nothing depends on it.
12. **"networkidle renders Angular"** (offline-inventory) **versus "no vf-root wait"** (kb-crawler). Both are true. Whether `networkidle` ever arrives on the eshop is unknown. Its pages load Dynatrace, Tealium (`utag` appears in 47 chunks) and `mqtt.min.js`, a messaging library that may keep a connection open.
13. One map read the demo profile's browsing history. I did not, and the plan should not rely on it. Its finding agrees with the cached route table: `/dsl/bundles` now lands on `dsl-landline`.

## 3. Gaps no map covered

1. **Replay reaches the live shop.** See the end of section 1. The 12 Nov cache entries could have come from such a replay session, so they neither prove nor disprove O29. Only the owner can say what happened.
2. **The first web-only Playwright sync will differ from the committed crawl in more than locators.** The committed knowledge base came from the in-browser crawler, with scripts off on CMS pages (yaml:94-95). The Playwright crawler runs scripts on every page. Owl carousels and other DOM built by scripts will appear, so churn may exceed the runbook's 68% estimate. The dry run settles it.
3. **Shop transactional pages would enter as ordinary pages.** The builder marks every page as `content` (`build.ts:259`). DSL checkout, subscription details, line numbers and review would therefore reach the page map and the experience profile unless the overlay marks them. Overlay entries match by page id, and shop ids are unstable, so marks and commit points in the overlay could silently stop applying.
4. **Ids built from prices.** Shop prices change often, so ids would churn. Scrubbing prices also renames ids such as `plus--37---600egp`. The overlay (3 entries), both evaluation sets and the experience profile must change in the same commit.
5. **Crawl folders keep page values.** The crawler saves each page's rendered HTML (`crawl.ts:130`) and item values in crawl.json (`extract.ts:226`). These sit in git-ignored `data/`, but a replay fixture made from them is committed. Nobody has decided whether these count under AGENTS 4.3. The web crawl already does this.
6. **The committed knowledge base cannot be rebuilt offline.** `data/crawls` is absent. To see what a price scrub does to router accuracy before a live sync, apply the scrub to a copy of the committed manifest and run `eval:router` on that copy.
7. **An offline test path for eshop pages already exists.**
   - What it does: offline replay serves saved pages for every site origin, the eshop included (`demo-browser.ts:297-301, 373, 381-386`). It runs inline scripts in the saved HTML and refuses every other script and API call (`:394-397`).
   - What it allows: a hand-written page served under the real eshop URL can test the loader, the agent guard and the journey fallback offline. No new localhost origin is needed.
   - What not to do: do not reuse the cached Vodafone JavaScript.
8. **Demo moment 6 conflicts with the agent guard.** "Sort by price" needs the agent on the shop (demo-script.md:67-73). Keeping the agent off the shop until commit points are marked therefore delays moment 6.
9. **The live plan has no eshop work.** It mentions the eshop only in one header fact (`docs/handoff/live-demos-way2.md:78`). §3.5 limits the Pocket to CMS pages, and ADR-0048 §1 says web only. Reading 2 is a plan change.

## 4. Owner decisions

**[blocks]** marks a decision that blocks the first step of a track.

**D1. What does "the pocket page" mean first?** [blocks Track B]
- Options: (a) Reading 1: eshop-linked web cards in the album; (b) Reading 2: the Pocket on eshop pages; (c) both now.
- Recommend (a) now inside phase 3, and (b) as a later sub-phase.
- Why: (a) reuses web's store and adapter and can be tested on saved pages. (b) needs real eshop markup, which does not exist on disk.

**D2. Which shop controls are commit points, and what happens to the agent until they are marked?** [blocks Track A step 1]
- Options: (a) Add to cart, Buy now, Reserve, Checkout, Choose a number, DSL order or subscribe, document upload and OTP, with the agent off on the shop until these are marked; (b) the same list, with the agent left on; (c) Buy now and checkout only.
- Recommend (a).
- Why: the agent runs on the shop today with an empty mask and no guard on its click tool (`agent.ts:46, 91`), and AGENTS 4.1 forbids pressing these. Moment 6 waits for this work.

**D3. Which eshop pages go into the knowledge base?** [blocks the scope step and the ADR]
- Options: (a) home, category lists, DSL and at-home landing pages, lines plans, with products as items of the lists; (b) (a) plus every product page; (c) the whole menu.
- Recommend (a), with a cap of about 40 shop pages.
- Why: product cards link to `#`, so the crawler cannot find product pages. Product pages would also churn with stock and multiply the price risk. Moments 5-6 need only the smartphones list.

**D4. Remove prices and stock from the knowledge base for every origin?** [blocks the scrub step]
- Options: (a) yes, everywhere, including ids, with a test that scans the manifest; (b) shop only; (c) no.
- Recommend (a), before the shop goes in.
- Why: this is AGENTS 4.3, and the knowledge base already holds about 265 such strings plus ids. It renames some web ids, so the evaluation sets and the overlay change in the same commit.

**D5. When may the shop be crawled live (lifting the 2026-10-23 stop)?** [blocks every live step]
- Options: (a) now, with today's config; (b) after O29 is updated and the safeguards in §6 are in place, owner-run and off-peak; (c) not yet.
- Recommend (b).
- Why: robots fails open, the agent has no guard on the shop, bot management is unknown, and O29 is open.

**D6. In what order do the syncs run?**
- Options: (a) a held web-only sync first, reviewed and activated, then a separate run that adds the shop; (b) one run of both origins.
- Recommend (a).
- Why: the web sync is expected to hold at about 68% churn. Keeping the shop out of it keeps that review readable, and the shop then appears cleanly as "added".

**D7. Which spelling of a category URL is canonical?**
- Options: (a) normalise `*x`, `/x` and `%2Fx` to one key; (b) keep whatever the shop shows in the address bar.
- Recommend (a), and record the live spelling as the variant URL.
- Why: measured with `norm.mts`, web links and the shop's own menu produce different keys today.

**D8. One Pocket across web and the eshop, or one per origin?** (Reading 2 only)
- Options: (a) a separate Pocket on each origin, and the album says so; (b) a same-site bridge frame under `/__vg`, demo browser only; (c) a store on our gateway; (d) stickers passed in the URL.
- Recommend (a), with (b) as a measured spike only if the owner wants one Pocket.
- Why: (c) and (d) move Vodafone's copy and prices out of the browser (ADR-0051, ADR-0039 §4). (b) depends on the demo browser's forwarding, which contradicts ADR-0048 §1.

**D9. Which eshop pages may the layer ever run on?** (Reading 2)
- Options: (a) an allowlist (home, category lists, product pages, DSL bundles), re-checked on every route change; (b) every `/(en|ar)/` path except robots-disallowed ones.
- Recommend (a), always excluding `/lines/*/numbers`.
- Why: a single-page app can route into the cart without loading a new page, and the layer checks the path only once (`demo-browser.ts:154`).

**D10. What may an eshop sticker keep?** (Reading 2)
- Options: (a) the same as web: copy as published, dated; (b) a dated price, but no stock or countdowns; (c) no prices.
- Recommend (b), and never anything from a cart, checkout or signed-in page.
- Why: stock and countdowns go out of date within minutes.

**D11. Should the owner make one signed-out visit to save eshop pages and facts?**
- Options: (a) yes, 4-6 pages, in a session of its own; (b) yes, together with the first shop crawl; (c) no.
- Recommend (a), first, and only after O29 is updated.
- Why: no-store means the cache will never hold eshop HTML. Reading 2 and the crawler's wait and scope rules all depend on what that visit saves.

**D12. What should the crawler's user agent say?**
- Options: (a) keep `VodafoneEG-VoiceGuide-Crawler/0.1`; (b) add a contact; (c) a project name plus a contact.
- Recommend (c), with a contact field in the config schema.
- Why: SPEC-04 §4 requires a contact. Before D3, a name that starts with Vodafone's can read as Vodafone's own crawler.

**D13. Should replay be truly offline?**
- Options: (a) `--replay` offline by default, with an explicit opt-in for live pages; (b) keep today's behaviour and fix the docs.
- Recommend (a).
- Why: replay demos currently open the live shop from sticker and "Buy now" links, while the console says offline.

**D14. Should traces stop holding read values, raw utterances and full URLs before the guide is used on shop forms?**
- Options: (a) yes; (b) no.
- Recommend (a).
- Why: AGENTS 4.3 and 4.4. Shop forms ask for national IDs and phone numbers. Read answers and utterances reach `trace_events` unmasked today (`executor.ts:154-157`; `server.ts:203-205`).

**D15. ADR number.** Not blocking. Recommend following the 2026-11-10 rule (order written) and updating the phase 3 map's references.
